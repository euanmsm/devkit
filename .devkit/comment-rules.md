# The Comment Contract

Every rule below governs comments in a hand-written source file — headers,
JSDoc, property docs and `//` lines. READMEs are not governed here.

This file is generated from `.devkit/terse.json`. A rule switched off there does
not appear here, so everything below is a rule this repository actually
enforces. Do not add rules from memory, and do not edit this file — edit the
config and regenerate.

Two kinds of rule, and neither outranks the other. Some are about **size** and
show up in a line count. Some are about **content** — what the sentence says —
and move no line count at all. A 50-character comment garbling two clauses of
behaviour costs a reader more than a long header that says one thing clearly.

## Coverage

### Every file opens with a header

A `// ====` banner block at the top of the file, before the imports.

**✗**

```typescript
import type { FastifyInstance } from 'fastify';

export default async function health(app: FastifyInstance): Promise<void> {
```

**✓**

```typescript
// ============================================================================
// Health Route
// ============================================================================
//
// Liveness for the box's monitoring. Says nothing about providers or database.

import type { FastifyInstance } from 'fastify';
```

### A file header is 8 lines, with no subsections

Three banner lines, one blank, then overview prose up to the cap. A header
carrying its own `---` underlined sections has become a document, and documents
do not live at the top of a source file.

### Every exported symbol and every function carries JSDoc

Const, type, interface, function — anything the file exports, and every function besides, so hovering any of them shows what it does. A plain value the file keeps to itself needs none.

In a file matching `\.test\.` or `\.spec\.` the `describe` and `it` names are the documentation, so there this binds only exported symbols.

Only top-level declarations count. A helper nested inside another function is
invisible to the scanner, which counts braces rather than parsing.

### Every property carries one line of JSDoc

Single-line `/** … */` form, saying **what the property is**. One sentence, one
clause — a full stop in the middle means it is too long. No default, no
constraint, no consequence, no rationale.

**✗**

```typescript
interface ServiceOptions {
  /** Postgres connection string. Migrations run against this before the listener opens, so a bad value fails startup. */
  databaseUrl: string;
}
```

**✓**

```typescript
interface ServiceOptions {
  /** Postgres connection string. */
  databaseUrl: string;
}
```

### JSDoc documents every parameter, the return and the throws

A block that exists is not the same as a block that says anything. Every
parameter in the signature gets a `@param` naming it, a function returning a
value gets a `@returns`, and a function with a `throw` of its own gets a
`@throws`. A `@param` naming a parameter the signature no longer has is a
finding too — that is a block left behind after a rename.

Only the allowed tags are required, so dropping one from that list drops it from
this rule too. A destructured parameter documents as one `@param` named for the
object, not as one per key.

**✗**

```typescript
/** Fetches a paper. */
function fetchPaper(id: string): Promise<Paper> {
  if (!id) throw new Error('no id');
  return db.papers.find(id);
}
```

**✓**

```typescript
/**
 * Fetches a paper.
 *
 * @param id - The paper's id
 * @returns The paper
 * @throws When the id is empty
 */
function fetchPaper(id: string): Promise<Paper> {
  if (!id) throw new Error('no id');
  return db.papers.find(id);
}
```

## JSDoc

### JSDoc is 4 prose lines, plus one line per tag

A one-line summary, then `@param` for every parameter and `@returns` for every
non-void return. Tag lines do not count against the cap. No body prose, and no
tag wrapping onto a second line. An object or destructured parameter gets one
`@param` for the object, not one per property.

### Allowed JSDoc tags: `@param`, `@returns`, `@throws`, `@deprecated`

No others. In particular no `@example` — link a test instead, which cannot rot.

## Logic comments

### A `//` comment is never required

Write one only when the code alone leaves a competent reader unsure, which means
one of:

- a **workaround** — a bug, quirk or limit in a library or service
- a **constraint invisible in the code** — ordering that matters, a race, timing
- the **origin of a magic value**
- **why the obvious approach fails**, where the code takes a stranger path
- **what a regex matches**

Restating the logic in English is an anti-pattern. The reader can read the code.

> **The test:** if deleting the comment loses nothing a competent reader would
> get from the code in five seconds, it should not exist.

### A logic comment is one line

Not "one, or two when needed". One. A constraint needing a paragraph needs a
different shape of code, or belongs in the pull request body.

## Style

### A comment states what the code is, right now

In one glanceable line. Not why it got that way, not what it used to be, not
what a reader might otherwise wonder.

### No history

No past tense about the code — `previously`, `used to`, `no longer`, `now that`,
`was originally`, `replaced`, `renamed`, `moved`. Git history keeps it.

**✗**

```typescript
// The loop previously polled every second, which was replaced with a queue.
```

**✓**

```typescript
// Leads arrive on the queue in batches of fifty.
```

### No conversation

No `as requested`, `per the plan`, `as discussed`, `Phase 2`, `we decided`,
`this issue`. A comment is read by someone who was not in the room and never
will be.

**✗**

```typescript
// As discussed, phase 2 moves this behind the flag.
```

**✓**

```typescript
// Runs only when the org has the beta flag set.
```

### No issue ids in comments

The one exception is a live `TODO(ABC-1234):` marker. An issue id in
ordinary prose points at a ticket the reader cannot open and does not need.

### State what is true, do not argue for it

No `because`, `so that`, `rather than`, `which is what`, `the reason`,
`deliberately`, `prevents`, `defaults to`, `falls back`, `otherwise`. Trade-offs
go in the pull request body, where they are reviewed and then archived.

**✗**

```typescript
// Retries three times rather than once, so that a flaky provider does not fail the run.
```

**✓**

```typescript
// Three attempts, two seconds apart.
```

### No first or second person

No `we`, `our`, `us`, `you`, `your`. Present tense, third person. The code has
no authors as far as a comment is concerned.

### One sentence, one clause, 100 characters

No semicolons, no stacked em-dash clauses, no subordinate-clause pile-ups. A
second sentence means there are two comments, and probably one too many.

**✗**

```typescript
// Builds the payload for the provider; note that the email field is optional here, and when absent the provider fills it from the account.
```

**✓**

```typescript
// An absent email is filled by the provider from the account.
```

## Hygiene

### No commented-out code

Delete it. Git history keeps it, and keeps it searchable, which a commented
block is not.

### `TODO(ABC-1234): one line` is the only marker form

No bare `TODO`, `FIXME`, `XXX` or `HACK`. No issue means no marker — file it or
fix it.

### Section banners split a file into its parts

A banner is welcome wherever a file has parts worth naming, at any length. A
file a reader takes in top to bottom has one part, and needs none.

### What a banner separates

One banner per part a reader would go looking for by name. In practice that is
the main export above and its helpers below, or the types a file declares ahead
of the logic that uses them. A banner over a single function is a label, not a
section, and a file with a banner every ten lines has a table of contents
instead of a shape.

```typescript
// ============================================================================
// Helpers
// ============================================================================
```

The one-line form does the same job where the file is dense with sections.

```typescript
// ======== Helpers ===========================================================
```

### A comment changes with the code it sits above, or it goes

Nothing accretes across commits. A comment describing behaviour the code no
longer has is worse than no comment, because it is believed.

### Cut content is deleted, never relocated

Not to a README, not to a doc comment further up, not anywhere. A reader who
needs to understand the code reads the code, and git history keeps the
archaeology. The only thing surviving a cut is one line naming a constraint the
code cannot express.

## Exceptions

### A migration header is exempt from the cap

A migration is a historical step, not the current state, and the table it
altered lives elsewhere. "Read the code" has nothing to point at, so the header
carries the reasoning and has no length cap.

Every content rule still binds every comment inside the file. Only the header's
length is exempt.

## Scope

The contract governs every file matching `\.(tsx?|mjs|cjs|js)$`, wherever it sits in the repository. Tests are included.

These paths are outside it:

- `(^|/)node_modules/`
- `\.min\.[cm]?js$`
- `\.d\.ts$`

## When a comment is borderline

If it answers **"what changed"**, it belongs in the commit message. If it
answers **"why did you"**, it belongs in the pull request body. If it answers
**"what is this"**, it is a comment.

## Enforcement

`terse` catches 17 of these in CI and refuses an edit that introduces one: `file-header`, `header-cap`, `exported-jsdoc`, `property-jsdoc`, `jsdoc-tag-coverage`, `jsdoc-cap`, `jsdoc-tags`, `logic-comment-length`, `no-history`, `no-conversation`, `no-issue-id`, `no-justification`, `no-person`, `comment-length`, `no-commented-code`, `todo-form`, `section-banner`.

No scanner can judge the rest, so they are review rules: `logic-comment-exception`, `what-not-why`, `comment-ages-with-code`, `cut-is-deleted`, `migration-exception`.
